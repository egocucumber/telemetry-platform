# ADR-0004: TimescaleDB для истории

**Статус:** принято

## Контекст

Запросы истории выглядят как «дай avg/min/max метрики X устройства Y между
t1 и t2 корзинами по N секунд». Сырые измерения приходят примерно по 100
строк в секунду на 20 устройств и должны храниться днями; минутные
агрегаты месяцами.

## Варианты

| Вариант | Замечания |
| --- | --- |
| Обычный PostgreSQL | Работает, но партиции и агрегаты придётся вести вручную |
| ClickHouse | Отличен для аналитики, но это второй движок и второй диалект в эксплуатации; избыточно для дашбордов по устройствам |
| InfluxDB | Создан для задачи, но отдельный язык запросов и слабая реляционная часть (устройствам, правилам и алертам тоже нужен дом) |
| **TimescaleDB** | PostgreSQL с гипертаблицами, continuous aggregates, retention и сжатием; одна база и для реляционных, и для временных данных |

## Решение

TimescaleDB.

* `measurements` это гипертаблица с часовыми чанками и уникальным индексом
  по `(device_id, metric, ts)`, который заодно служит защитой
  идемпотентности.
* `measurements_1m` это continuous aggregate с real-time материализацией
  (`materialized_only = false`), поэтому запрос за последнюю минуту сливает
  материализованные корзины со свежими сырыми строками.
* Retention: сырые данные 7 дней, минутные агрегаты 90 дней.
* Запись идёт одним `INSERT … SELECT FROM unnest(...)` на батч: один
  round-trip на тысячи строк и совместимость с `ON CONFLICT` (чего у `COPY`
  нет).

Query-сервис выбирает источник сам: шаги, кратные минуте, читаются из
агрегата, более мелкие из сырых данных.
