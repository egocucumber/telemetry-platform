# ADR-0002: Доставка at-least-once с идемпотентными приёмниками

**Статус:** принято

## Контекст

Processor читает батч из Kafka и пишет в три места: TimescaleDB, Redis и
Kafka (алерты). Распределённой транзакции между ними нет. Транзакции самой
Kafka покрывают только путь Kafka → Kafka.

## Решение

Коммитить оффсеты **после** успеха всех приёмников и сделать каждый
приёмник устойчивым к повтору:

| Приёмник | Механизм идемпотентности |
| --- | --- |
| Сырые измерения в TimescaleDB | `INSERT … ON CONFLICT (device_id, metric, ts) DO NOTHING` через `unnest` |
| Redis `latest:{device}` | Lua-скрипт оставляет значение с самым новым timestamp |
| Redis `window:{device}` | Простая перезапись; повтор пишет то же закрытое окно |
| Топик алертов | ID алерта это UUID, созданный в момент смены состояния; alerter делает upsert по ID |
| Уведомления | Ключ cooldown в Redis (`SET NX PX`), поэтому повторное событие FIRING не будит второй раз |

Если отправка алертов не удалась, записи откладываются в `Pipeline.pending`
и отправляются перед повторной обработкой батча. Движок правил для
повторённых измерений *не* пересчитывается (его состояние уже продвинулось),
поэтому алерт уходит ровно один раз, хотя батч обработан дважды.

Тот же контракт действует выше по потоку: ingest подтверждает измерение
только после `acks=all` и дедуплицирует повторы через `SET NX` по ключу
`device_id:seq`. Клиент, не дождавшийся ответа, шлёт тот же батч и получает
`DUPLICATE` для того, что уже легло.

## Почему не exactly-once через транзакции Kafka

Они покрыли бы только переход `telemetry.raw → telemetry.alerts`. Запись в
базу и Redis всё равно вне Kafka, значит идемпотентные приёмники нужны в
любом случае; а раз они есть, транзакции добавляют задержку и сложность
эксплуатации без дополнительных гарантий.

## Последствия

* Обработчики должны безопасно переживать повторный запуск. Это закреплено
  соглашением и интеграционным тестом `TestKafkaAtLeastOnce`.
* Объём повторной работы при replay ограничен `BATCH_SIZE`.
