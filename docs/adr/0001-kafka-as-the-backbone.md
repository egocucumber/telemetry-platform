# ADR-0001: Kafka как шина событий

**Статус:** принято

## Контекст

Телеметрия приходит от множества шлюзов с высокой и неравномерной
интенсивностью. Один и тот же поток нужен нескольким независимым
потребителям (хранение, правила, позже ML или экспорт), у каждого свой темп
и свои отказы. Медленный потребитель не должен создавать обратное давление
на станки в цеху.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Прямая запись из ingest в БД и Redis | Просто, без брокера | Задержка ingest ограничена самым медленным приёмником; нет replay; новый потребитель требует правки ingest |
| NATS JetStream | Лёгкий, простая эксплуатация | Слабее экосистема для паттернов уровня exactly-once, партиции не первоклассная сущность |
| RabbitMQ | Зрелый, гибкая маршрутизация | Семантика очереди (сообщение удаляется после ack), replay неудобен, порядок по ключу не естественен |
| **Kafka (KRaft)** | Долговечный лог, replay, consumer group'ы, партиционирование по ключу, огромная экосистема | Тяжелее в эксплуатации |

## Решение

Kafka, ключ сообщения `device_id`.

* **Порядок в рамках устройства** вытекает из партиционирования по ключу. На
  него опираются движок правил и агрегатор окон: их состояние хранится по
  устройству в памяти того экземпляра processor, который владеет партицией.
* **Развязка**: ingest подтверждает батч после `acks=all`; если TimescaleDB
  лежит десять минут, ничего не теряется и ни один шлюз этого не замечает.
* **Replay**: новую read-модель можно построить из сохранённого лога.
* **Горизонтальное масштабирование** сводится к ребалансу consumer group,
  без изменений кода.

Клиентская библиотека: `franz-go`. Быстрее `sarama` и `kafka-go`,
идемпотентный продюсер по умолчанию, cooperative-sticky ребаланс и явный
контроль над коммитами и блокировкой ребаланса (`BlockRebalanceOnPoll`).

## Последствия

* В Compose один брокер KRaft; фактор репликации 1 только для разработки
  (партиции и retention заданы в `kafkax.DefaultTopics`).
* Формат сообщений protobuf (`TelemetryEvent`, `AlertEvent`), общий с gRPC
  API, поэтому у эволюции схемы один источник истины.
