# Нагрузочный тест

Метод: стек Compose по умолчанию (один брокер Kafka, 2 реплики processor,
TimescaleDB с настройками по умолчанию, Redis) плюс второй симулятор на
хосте в режиме `make load`:

```
DEVICES=200 INTERVAL=500ms INCIDENT_RATE=0.001 go run ./cmd/simulator
```

200 станков × 5 метрик каждые 500 мс = целевые 2 000 измерений/с, по
одному батчу из 1 000 измерений на сообщение стрима. Длительность 120 с.
Метрики сняты с `/metrics` до и после; квантили интерполированы по корзинам
гистограмм Prometheus. Демо-парк из 20 станков работал одновременно.

Железо: ноутбук, Windows 11, Docker Desktop (бэкенд WSL2). Абсолютные
цифры ориентировочные; важна форма распределения и то, что ничего не
падает.

## Наблюдения

* Вставка в базу занимает большую часть времени processor. Это уже один
  запрос на батч; следующий рычаг это батчи покрупнее (`BATCH_SIZE` или
  `FetchMaxWait`), обмен задержки на пропускную способность, а для долгих
  прогонов сжатие TimescaleDB и подбор `chunk_time_interval`.
* p99 ingest определяется round-trip'ами `acks=all` на одном брокере внутри
  Docker Desktop; на реальном кластере с отдельными дисками он резко падает.
* Ни ошибок, ни записей в DLQ, ни роста лага: процессоры успевали за
  продюсером (`processor_batch_size` держался в десятках, а не у потолка
  2 000).
* Воспроизвести: `make load` и дашборд *Telemetry Platform* в Grafana.
